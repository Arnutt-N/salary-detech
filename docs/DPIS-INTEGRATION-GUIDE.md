## 1. ภาพรวม 2 ทางเลือกการเชื่อมต่อ

| | ทางเลือกที่ 1 — **Push API** | ทางเลือกที่ 2 — **SQL Views + Agent** |
|---|---|---|
| หลักการ | ฝั่ง DPIS ส่งข้อมูลเข้า API ของ Salary Detech ด้วย HTTPS | Salary Detech ดึงข้อมูลจาก SQL Views บนฐานข้อมูล DPIS ผ่านตัว agent ที่รันในเครือข่ายราชการ |
| ความเหมาะสม | **เริ่มต้นเร็วสุด** เหมาะทำก่อน / เหมาะกับข้อมูลที่ต้องการส่งทันที | เหมาะกับการรันอัตโนมัติเป็นรอบ (เช่น ทุกคืน) โดยไม่ต้องเขียนตัวส่งเอง |
| สิ่งที่ฝั่ง DPIS ต้องทำ | เขียนตัวส่ง (HTTP POST + JSON) หรือใช้เครื่องมือ ETL ที่มีอยู่ | สร้าง SQL Views 3 ตัว + เปิด DB account แบบ read-only + เตรียมเครื่อง/VM สำหรับ agent |
| ความปลอดภัย | ไม่ต้องเปิดการเข้าถึงฐานข้อมูล DPIS ออกภายนอก (outbound HTTPS เท่านั้น) | DB account ต้องเป็น **read-only เท่านั้น** และ agent รันในเครือข่ายราชการ |

**ทั้ง 2 ทางเลือกใช้ pipeline บันทึกข้อมูลชุดเดียวกัน** — ไม่ว่าข้อมูลจะเข้าทางใด ผลลัพธ์ในระบบและการตรวจสอบความสดใหม่ (freshness) เหมือนกันทุกประการ จึงเลือกใช้พร้อมกันได้ (เช่น เริ่มด้วย Push แล้วเปลี่ยนมา Pull ภายหลัง)

**ข้อตกลงสำคัญของ pipeline:** การส่งซ้ำกี่รอบก็ได้ผลลัพธ์เหมือนเดิม (idempotent) — ข้อมูลบุคคล upsert ตามเลขบัตรประชาชน และคำสั่ง dedupe ตาม (เลขที่คำสั่ง, ผู้เกี่ยวข้อง) ดูรายละเอียดใน §2.5

## 2. ทางเลือกที่ 1: Push API

### 2.1 Base URL และการยืนยันตัวตน

- **Base URL (staging):** `https://<staging-host>` — ขอจากผู้ดูแลระบบ Salary Detech
- **Base URL (production):** `https://<production-host>` — ขอจากผู้ดูแลระบบ Salary Detech
- **การยืนยันตัวตน:** แนบ header ทุกคำขอ:

  ```
  Authorization: Bearer <INTEGRATION_SECRET>
  ```

- **การขอรหัส `INTEGRATION_SECRET`:** ติดต่อผู้ดูแลระบบ Salary Detech ทางช่องทางใน §6 — รหัสจะส่งผ่านช่องทางที่ปลอดภัยเท่านั้น
- **การเก็บรหัสอย่างปลอดภัย:** เก็บใน environment variable ของระบบ/เครื่องที่รันตัวส่ง **ห้าม hardcode ในโค้ด ห้าม commit ลง git และห้ามส่งในอีเมล/แชทธรรมดา**

รหัสสถานะที่เกี่ยวกับการยืนยันตัวตน:

| รหัส | ความหมาย | สิ่งที่ต้องทำ |
|------|----------|--------------|
| `401` | ไม่แนบ header หรือรหัสไม่ถูกต้อง | ตรวจรูปแบบ `Bearer <secret>` (มีเว้นวรรคหลังคำว่า Bearer) |
| `503` | ฝั่งเซิร์ฟเวอร์ **ยังไม่ได้ตั้ง** `INTEGRATION_SECRET` (fail-closed) | แจ้งผู้ดูแลระบบ Salary Detech — ไม่ใช่ความผิดของตัวส่ง |

### 2.2 Endpoint ซิงค์ข้อมูลข้าราชการ

```
POST /api/v1/integrations/employees/sync
```

- รับได้ทั้ง object เดี่ยว หรือ array (สูงสุด 1,000 รายการ/คำขอ)
- Upsert อัตโนมัติ: พบเลขบัตรประชาชนเดิม → **อัปเดต** ไม่พบ → **สร้างใหม่**
- ตรวจข้อมูลรายแถวด้วย schema validation — แถวที่ผิดจะถูกรายงานใน `errors` ของแถวนั้น ไม่กระทบแถวอื่น

**ตารางฟิลด์ (คีย์ชื่อตาม DPIS):**

| ฟิลด์ | ชนิด | บังคับ | คำอธิบาย |
|-------|------|--------|----------|
| `per_cardno` | string | ⚠️ เงื่อนไข | เลขประจำตัวประชาชน 13 หลัก — **คีย์หลักของการ upsert** (ต้องมี `per_cardno` หรือ `per_name` อย่างน้อย 1 ฟิลด์) |
| `per_name` | string | ⚠️ เงื่อนไข | ชื่อตัว |
| `per_surname` | string | — | นามสกุล |
| `pn_name` | string | — | คำนำหน้าชื่อ (นาย/นาง/นางสาว) |
| `per_id` | number หรือ string | — | เลขประจำตัวข้าราชการใน DPIS |
| `pos_name` | string | — | ชื่อตำแหน่งปัจจุบัน |
| `pos_no` | string | — | เลขที่ตำแหน่งปัจจุบัน |
| `pt_name` | string | — | ประเภทตำแหน่ง (วิชาการ/ทั่วไป/อำนวยการ/บริหาร) |
| `level_no` | string | — | ระดับตำแหน่งรหัส (O1–E2) |
| `level_name` | string | — | ระดับตำแหน่งชื่อ (ใช้ `level_name` ก่อน `level_no` ถ้าส่งทั้งคู่) |
| `org_name_bureau` | string | — | สังกัดระดับสำนัก/กอง |
| `org_name_division` | string | — | สังกัดระดับกอง/แผนก |
| `org_name_department` | string | — | สังกัดระดับกรม |
| `org_name_ministry` | string | — | สังกัดระดับกระทรวง |
| `per_salary` | number หรือ string | — | เงินเดือนปัจจุบัน |
| `salary_system_type` | string | — | ระบบเงินเดือน (ไม่ส่ง = ค่าเริ่มต้น `"แท่ง"`) |
| `per_gender` | number หรือ string | — | เพศ |
| `per_birthdate` | string | — | วันเกิด (รูปแบบวันที่ §2.4) |
| `per_startdate` | string | — | วันเข้ารับราชการ |
| `per_retiredate` | string | — | วันเกษียณ |
| `per_active` | number หรือ string | — | `1` = ปฏิบัติงาน, `0` = ไม่ปฏิบัติงาน (ไม่ส่ง = ปฏิบัติงาน) |

> ฟิลด์อื่น ๆ ของ DPIS ที่ไม่อยู่ในตารางจะถูก **เมินผ่าน (tolerated)** — ตัวส่งไม่ต้องกรองคอลัมน์ให้เป๊ะก่อน

**ตัวอย่าง request:**

```bash
curl -X POST "$BASE_URL/api/v1/integrations/employees/sync" \
  -H "Authorization: Bearer $INTEGRATION_SECRET" \
  -H "Content-Type: application/json" \
  -d '{
    "per_cardno": "1100200300401",
    "pn_name": "นาย",
    "per_name": "สมชาย",
    "per_surname": "รักชาติ",
    "pos_name": "นักวิเคราะห์นโยบายและแผน",
    "level_name": "ชำนาญการ",
    "org_name_ministry": "กระทรวงการคลัง",
    "per_salary": "35000",
    "per_active": 1
  }'
```

**ตัวอย่าง response (สำเร็จ):**

```json
{
  "success": true,
  "data": { "total": 1, "created": 1, "updated": 0, "errors": [] }
}
```

| ฟิลด์ผลลัพธ์ | ความหมาย |
|--------------|----------|
| `total` | จำนวนแถวที่รับทั้งหมด |
| `created` | จำนวนที่สร้างใหม่ |
| `updated` | จำนวนที่อัปเดตของเดิม (เลขบัตรซ้ำ) |
| `errors` | รายการข้อผิดพลาดรายแถว (`citizenId` + `error`) |

### 2.3 Endpoint ซิงค์ข้อมูลคำสั่ง

```
POST /api/v1/integrations/orders/sync
```

- รับได้ทั้ง object เดี่ยว หรือ array (สูงสุด 1,000 รายการ/คำขอ)
- **คำสั่งต้องมีข้อมูลบุคคลในระบบก่อน** — ระบบค้นหาผู้เกี่ยวข้องจาก `per_cardno` (หรือระบุ `employee_id` ตรงถ้ารู้) ถ้าไม่พบจะได้ error `"Person not found in database. Please sync employee first."` → **ลำดับที่ถูกต้องคือ sync ข้อมูลบุคคล (§2.2) ก่อนเสมอ**
- คำสั่งที่บันทึกสำเร็จจะมีสถานะ `active` และถูก **ตรวจความสดใหม่ (freshness) ทันที** ทั้งเงินเดือน/ตำแหน่ง/ประเภท/ระดับ/สังกัด พร้อมตรวจผลกระทบลูกโซ่ (cascade) กับคำสั่งอื่นของคนเดียวกัน

**ตารางฟิลด์:**

| ฟิลด์ | ชนิด | บังคับ | คำอธิบาย |
|-------|------|--------|----------|
| `com_no` | string | แนะนำให้ส่ง | เลขที่คำสั่ง — **ใช้เป็นคีย์กันข้อมูลซ้ำ (dedupe)** ดู §2.5 (ไม่ส่ง = ไม่มีคีย์ dedupe) |
| `com_date` | string | — | วันที่ออกคำสั่ง (ไม่ส่ง = ใช้ `cmd_date`) |
| `cmd_date` | string | แนะนำให้ส่ง | **วันที่คำสั่งมีผล** (ไม่ส่ง = ใช้วันที่ของระบบ ณ ตอนรับ — ไม่แนะนำ) |
| `mov_code` | string | แนะนำให้ส่ง | รหัสประเภทการเคลื่อนไหว — กำหนดประเภทคำสั่ง (ตาราง §2.4) |
| `cmd_seq` | number หรือ string | — | ลำดับที่ในบัญชีแนบท้ายคำสั่ง |
| `per_cardno` | string | ⚠️ เงื่อนไข | เลขบัตรประชาชนผู้เกี่ยวข้อง — ใช้ค้นหาบุคคลในระบบ (ต้องมี `per_cardno` หรือ `employee_id`) |
| `employee_id` | number | ⚠️ เงื่อนไข | id ภายในระบบ Salary Detech (ถ้ารู้ค่า ใช้แทน `per_cardno` ได้) |
| `cmd_salary` | number หรือ string | — | อัตราเงินเดือนใหม่ตามคำสั่ง |
| `cmd_spsalary` | number หรือ string | — | เงินตอบแทนพิเศษ |
| `cmd_old_salary` | number หรือ string | — | อัตราเงินเดือนเดิมก่อนคำสั่งมีผล |
| `cost_of_living` | number หรือ string | — | เงินเพิ่มการครองชีพชั่วคราว |
| `pos_allowance` | number หรือ string | — | เงินประจำตำแหน่ง |
| `salary_as_of_date` | string | — | เงินเดือน ณ วันที่ (ไม่ส่ง = ใช้ `cmd_date`) |
| `pos_name` | string | — | ชื่อตำแหน่งใหม่ |
| `pos_no` | string | — | เลขที่ตำแหน่งใหม่ |
| `pt_name` | string | — | ประเภทตำแหน่งใหม่ |
| `level_no` / `level_name` | string | — | ระดับตำแหน่งใหม่ (ใช้ `level_name` ก่อนถ้าส่งทั้งคู่) |
| `org_bureau` | string | — | สังกัดใหม่: สำนัก/กอง |
| `org_division` | string | — | สังกัดใหม่: กอง/แผนก |
| `org_subdivision` | string | — | สังกัดใหม่: แผนกย่อย |
| `org_department` | string | — | สังกัดใหม่: กรม |
| `org_ministry` | string | — | สังกัดใหม่: กระทรวง |
| `cmd_position` | string | — | ตำแหน่งเดิม (ฝั่งเดิม) |
| `cmd_level` | string | — | ระดับตำแหน่งเดิม |
| `cmd_org1` | string | — | สังกัดเดิม: กระทรวง |
| `cmd_org2` | string | — | สังกัดเดิม: กรม |
| `cmd_org3` | string | — | สังกัดเดิม: สำนัก/กอง |
| `cmd_org4` | string | — | สังกัดเดิม: ฝ่าย/กลุ่ม |
| `cmd_org5` | string | — | สังกัดเดิม: ระดับอื่น |
| `note` | string | — | หมายเหตุ |

> ฟิลด์อื่น ๆ นอกตารางจะถูกเมินผ่านเช่นเดียวกับข้อมูลบุคคล

**ตัวอย่าง request (array 2 รายการ):**

```bash
curl -X POST "$BASE_URL/api/v1/integrations/orders/sync" \
  -H "Authorization: Bearer $INTEGRATION_SECRET" \
  -H "Content-Type: application/json" \
  -d '[
    {
      "com_no": "125/2569",
      "com_date": "2569-05-10",
      "cmd_date": "2569-05-01",
      "mov_code": "20100",
      "cmd_salary": "25500",
      "cmd_old_salary": "25000",
      "per_cardno": "1100200300401"
    },
    {
      "com_no": "126/2569",
      "com_date": "2569-05-10",
      "cmd_date": "2569-05-01",
      "mov_code": "30200",
      "cmd_salary": "22000",
      "pos_name": "นักจัดการงานทั่วไป",
      "org_bureau": "กองการเจ้าหน้าที่",
      "per_cardno": "1100200300402"
    }
  ]'
```

**ตัวอย่าง response (สำเร็จ):**

```json
{
  "success": true,
  "data": {
    "total": 2,
    "created": 2,
    "skipped": 0,
    "updated": 0,
    "staleFound": 0,
    "cascaded": 0,
    "errors": []
  }
}
```

| ฟิลด์ผลลัพธ์ | ความหมาย |
|--------------|----------|
| `total` | จำนวนแถวที่รับทั้งหมด |
| `created` | จำนวนคำสั่งที่สร้างใหม่ |
| `skipped` | จำนวนที่ **ข้าม** เพราะเป็นคำสั่งเดิม (เลขที่คำสั่ง+ผู้เกี่ยวข้องเดิม) ที่ข้อมูลเหมือนเดิมทุกอย่าง (§2.5) |
| `updated` | จำนวนคำสั่งเดิมที่ถูก **อัปเดต** ตามข้อมูลที่ส่งมาใหม่ (§2.5) |
| `staleFound` | จำนวนคำสั่งที่ผลตรวจ freshness ระบุว่า `stale` (ข้อมูลในคำสั่งไม่ตรงข้อเท็จจริง ณ วันที่มีผล) |
| `cascaded` | จำนวนคำสั่ง **อื่น** ของบุคคลเดียวกันที่ได้รับผลจากการตรวจลูกโซ่ (cascade) |
| `errors` | รายการข้อผิดพลาดรายแถว (`comNo` + `citizenId` + `error`) |

**ตัวอย่าง response เมื่อมีบางแถวผิด (partial success — HTTP 200):**

```json
{
  "success": true,
  "data": {
    "total": 2,
    "created": 1,
    "skipped": 0,
    "updated": 0,
    "staleFound": 0,
    "cascaded": 0,
    "errors": [
      {
        "comNo": "127/2569",
        "citizenId": "0000000000000",
        "error": "Person not found in database. Please sync employee first."
      }
    ]
  }
}
```

### 2.4 รูปแบบวันที่และรหัสการเคลื่อนไหว (mov_code)

**รูปแบบวันที่ที่รองรับ** (ทุกฟิลด์วันที่):

| รูปแบบที่ส่งมา | ตัวอย่าง | ผลที่เก็บในระบบ |
|----------------|----------|-----------------|
| `YYYY-MM-DD` | `2569-05-01` | เก็บตามเดิม `2569-05-01` (**แนะนำรูปแบบนี้** — ตรงกับที่ระบบใช้ทั้งหมด) |
| `YYYY-MM-DD HH:mm:ss` | `2569-05-01 00:00:00` | ตัดเวลาทิ้ง → `2569-05-01` |

### 2.5 พฤติกรรมเมื่อส่งข้อมูลซ้ำ (Idempotency)

> ส่วนนี้เป็น **contract ที่มีผลตั้งแต่ ส.ค. 2569** — ตัวส่งสามารถส่งข้อมูลซ้ำได้อย่างปลอดภัย (เช่น รันซ้ำหลัง network หลุด) โดยไม่เกิดข้อมูลซ้ำในระบบ

**ข้อมูลบุคคล (employees/sync):** upsert ตามเลขบัตรประชาชนอยู่แล้ว — ส่งซ้ำ = อัปเดตของเดิม (`created: 0, updated: 1`)

**คำสั่ง (orders/sync)** — ระบบมองหาคำสั่งเดิมด้วยคู่คีย์ **(เลขที่คำสั่ง `com_no`, ผู้เกี่ยวข้อง)**:

| กรณี | พฤติกรรมของระบบ | ผลลัพธ์ |
|------|-----------------|---------|
| มี `com_no` + เป็นคำสั่งเดิม + ข้อมูล snapshot **เหมือนเดิมทุกอย่าง** | ข้าม ไม่เขียนอะไร | นับใน `skipped` |
| มี `com_no` + เป็นคำสั่งเดิม + ข้อมูล **เปลี่ยน** (เช่น `cmd_salary` แก้) | อัปเดตฟิลด์ snapshot ให้ตรงต้นทาง + **ตรวจ freshness และ cascade ใหม่ทั้งชุด** | นับใน `updated` (+ `staleFound`/`cascaded` ถ้ามี) |
| มี `com_no` + ยังไม่เคยมีในระบบ | สร้างใหม่ | นับใน `created` |
| **ไม่มี `com_no`** (null) | สร้างใหม่ทุกครั้ง — **ไม่มีการ dedupe** เพราะไม่มีคีย์ | นับใน `created` |

หมายเหตุ:
- การอัปเดตคำสั่งเดิม **ไม่แตะสถานะวงจรชีวิตของคำสั่งในระบบ** (เช่น ถ้าคำสั่งถูกยกเลิกในระบบเรา จะยังคงสถานะเดิมไว้) — เฉพาะฟิลด์ snapshot จากต้นทางเท่านั้นที่ถูกอัปเดต
- เลขที่คำสั่งเดียวกันคนละคน (เช่น คำสั่งตำแหน่งที่มีหลายรายชื่อ) ถือเป็นคำสั่งคนละรายการ — ส่งได้ปกติ

### 2.6 ข้อจำกัด รหัสสถานะ และแนวทาง Retry

**ข้อจำกัด:**

- สูงสุด **1,000 รายการต่อคำขอ** — เกินจะได้ `413` ให้แบ่งส่งเป็นชุด ๆ (ระบบแนะนำ chunk 500 ต่อคำขอ)
- ตรวจข้อมูลเป็น **รายแถว** — แถวที่ผิดรูปแบบไม่ทำให้ทั้งชุดล้ม (HTTP 200 พร้อม `errors` รายแถว)
- คำสั่งต้องมีบุคคลในระบบก่อน (§2.3)

**ตารางรหัสสถานะ:**

| รหัส | กรณี | แนวทาง |
|------|------|--------|
| `200` | สำเร็จ (ตรวจ `errors` รายแถวเสมอ) | — |
| `400` | body ว่าง / รูปแบบ body ผิด | แก้ request |
| `401` | ไม่แนบ / แนบ `Authorization` ผิด | ตรวจ secret |
| `413` | เกิน 1,000 รายการ | แบ่ง batch |
| `500` | ข้อผิดพลาดฝั่งเซิร์ฟเวอร์ | retry |
| `503` | ฝั่งเซิร์ฟเวอร์ยังไม่ตั้ง `INTEGRATION_SECRET` | แจ้งผู้ดูแลระบบ — **ห้าม retry รัว ๆ** |

**แนวทาง retry:**

1. ตัวส่งควร retry เฉพาะ `429`/`500`/`503` (ฝั่งเซิร์ฟเวอร์) และความผิดพลาดระดับเครือข่าย (timeout / connection refused)
2. ใช้ backoff แบบขยายเวลา (เช่น 1 → 5 → 30 วินาที) จำกัดไม่เกิน ~5 รอบ
3. `400`/`401`/`413` **ไม่ต้อง retry** — เป็นข้อผิดพลาดของ request ที่ต้องแก้ต้นเหตุ
4. เพราะ pipeline เป็น idempotent (§2.5) — ส่งซ้ำหลังหลุดกลางทางได้ปลอดภัย ระบบจะข้าม/อัปเดตให้เอง
5. ควรบันทึก `errors` รายแถวไว้ทบทวน แล้วส่งเฉพาะแถวที่แก้แล้วในรอบถัดไป

### 2.7 API ตรวจสอบสถานะก่อนจ่ายเงินเดือน (สำหรับฝั่ง Payroll)

## 3. ทางเลือกที่ 2: Pull ด้วย SQL Views + Agent

เหมาะกับการซิงค์อัตโนมัติเป็นรอบ — Salary Detech เตรียม SQL Views 3 ตัวให้สร้างบนฐานข้อมูล DPIS:

1. `vw_dpis_salary_detech_person` — ข้อมูลข้าราชการปัจจุบัน (ตำแหน่ง สังกัด เงินเดือน)
2. `vw_dpis_salary_detech_order` — คำสั่ง + บัญชีแนบท้าย (snapshot เดิม/ใหม่)
3. `vw_dpis_salary_detech_salary_history` — ประวัติเงินเดือนย้อนหลัง

ไฟล์สคริปต์: [`scripts/dpis-integration-pipeline.sql`](../scripts/dpis-integration-pipeline.sql) (เขียนสไตล์ MySQL — จะปรับ dialect ตาม engine จริงของฐานข้อมูล DPIS หลังยืนยัน)

**สิ่งที่ฝั่ง DPIS ต้องเตรียม:**

| รายการ | รายละเอียด |
|--------|-----------|
| 1. สร้าง Views | รันสคริปต์ SQL ด้านบนบนฐานข้อมูล DPIS (จะได้ views แบบ read-only ไม่แตะตารางต้นทาง) |
| 2. DB account read-only | สร้าง account ที่ `SELECT` ได้ **เฉพาะ 3 views นี้** — ห้ามสิทธิ์เขียน/แก้/ลบโดยเด็ดขาด |
| 3. เครื่อง/VM สำหรับ agent | เครื่องในเครือข่ายราชการที่ (ก) เข้าฐานข้อมูล DPIS ได้ (ข) ออก internet ไปยัง Salary Detech ได้ (HTTPS) |
| 4. ปฏิทินการรัน | ตกลงรอบซิงค์ (เช่น ทุกวัน 02:00 น.) — ตั้งผ่าน Task Scheduler (Windows) หรือ cron (Linux) |
| 5. Secret | ตั้ง `INTEGRATION_SECRET` เป็น env ของเครื่อง agent (รูปแบบ A-1: agent ดึง views แล้ว push เข้า API ของเรา) |

**ขั้นตอนตั้งเวลา (ตัวอย่าง):**

```bash
# Linux cron — รันทุกวัน 02:00 น.
0 2 * * * cd /opt/salary-detech-agent && npx tsx scripts/dpis-pull-agent.ts >> /var/log/dpis-agent.log 2>&1
```

```powershell
# Windows Task Scheduler (เรียกเป็น batch) — รันทุกวัน 02:00 น.
schtasks /create /tn "DPIS-Sync" /tr "cmd /c cd /d D:\salary-detech-agent && npx tsx scripts/dpis-pull-agent.ts" /sc daily /st 02:00
```

> **สถานะ:** ตัว agent (`scripts/dpis-pull-agent.ts`) อยู่ระหว่างพัฒนาตามแผน P7 Phase 2–3 — ทางเลือกนี้จะพร้อมใช้หลังตอบคำถามเตรียมข้อมูล (engine ของฐานข้อมูล / เครื่อง agent / ปริมาณข้อมูล) ครบ ในระหว่างนี้ใช้ทางเลือกที่ 1 (Push API) ได้ทันที

## 5. FAQ

**Q: ได้ `401 Unauthorized` ทุกครั้ง?**
A: ตรวจว่า header เป็น `Authorization: Bearer <secret>` ครบทั้งคำ `Bearer` + เว้นวรรค + ตัวรหัส (ไม่มีอักขระเกิน/ขาด เช่น เครื่องหมายคำพูดติดมาด้วย)

**Q: ได้ `503` พร้อมข้อความ "INTEGRATION_SECRET is not configured"?**
A: ฝั่งเซิร์ฟเวอร์ Salary Detech ยังไม่ได้ตั้งรหัส (ระบบออกแบบแบบ fail-closed — ไม่มีรหัส = ปฏิเสธทุกคำขอ) แจ้งผู้ดูแลระบบ ไม่ต้องแก้ฝั่งตัวส่ง

**Q: ได้ error "Person not found in database. Please sync employee first."?**
A: คำสั่งอ้างถึงบุคคลที่ยังไม่มีในระบบ — ส่งข้อมูลบุคคล (§2.2) ก่อนคำสั่ง (§2.3) เสมอ ใน batch เดียวกันก็ให้เรียงบุคคลมาก่อนคำสั่ง

**Q: ส่งข้อมูลซ้ำเพราะไม่แน่ใจว่ารอบก่อนสำเร็จหรือไม่ จะเกิดข้อมูลซ้ำไหม?**
A: ไม่เกิด — ระบบ idempotent (§2.5): บุคคล upsert ตามเลขบัตร, คำสั่ง dedupe ตาม (เลขที่คำสั่ง, ผู้เกี่ยวข้อง) ข้อมูลเหมือนเดิม → `skipped`, เปลี่ยน → อัปเดตตามต้นทาง

**Q: แถวผิดบางแถวทำให้ทั้ง batch ล้มไหม?**
A: ไม่ — ระบบบันทึกแถวที่ถูกต้องตามปกติ แล้วรายงานแถวที่ผิดใน `errors` (HTTP 200) ให้นำรายการใน `errors` ไปแก้แล้วส่งซ้ำเฉพาะแถวนั้น

**Q: ได้ `413` เมื่อส่งหลายพันรายการ?**
A: แบ่งส่งชุดละไม่เกิน 1,000 รายการ (แนะนำ 500) — ส่งต่อกันได้เรื่อย ๆ

**Q: วันที่ควรส่งรูปแบบไหน?**
A: `YYYY-MM-DD` (พ.ศ. ตามที่ฐานข้อมูล DPIS ใช้ เช่น `2569-05-01`) — อย่าผสมรูปแบบในข้อมูลชุดเดียวกัน ดูตาราง §2.4 และข้อควรระวังปี พ.ศ./ค.ศ.

**Q: จะรู้ได้อย่างไรว่าคำสั่งที่ส่งไปถูก flag ว่า stale?**
A: ดู `staleFound` ใน response ของ orders/sync หรือเรียก freshness-check (§2.7) เพื่อดูรายละเอียดมิติที่ stale

**Q: ต้องส่งทุกฟิลด์ไหม?**
A: ไม่ — ฟิลด์ที่ไม่ส่งจะเป็นค่าว่าง ยกเว้นที่มีกติกาเงื่อนไขตามตาราง (เช่น บุคคลต้องมีเลขบัตรหรือชื่อ, คำสั่งต้องมี `per_cardno` หรือ `employee_id`)
